# Plan de Sustentabilidad del Primer Producto

**Empresa:** Magic Leaf Studios  
**Producto:** Prototipo  
**País:** Bolivia  
**Versión:** 2.0 · Septiembre de 2026

## 1. Propósito

Definir cómo el equipo llevará el Prototipo desde la preproducción hasta su validación y posible evolución, usando los recursos mínimos disponibles y protegiendo la calidad, el flujo de caja y la propiedad intelectual.

La sustentabilidad del primer producto se medirá por su capacidad para:

- Llegar a una versión publicable dentro del alcance aprobado.
- Mantener el desarrollo con un equipo inicial pequeño.
- Generar ingresos suficientes para cubrir soporte y mejoras prioritarias.
- Conservar el código, los assets y el conocimiento del proyecto.
- Evitar gastos fijos que no sean necesarios antes de validar la demanda.

## 2. Alcance del plan

El plan aplica a cinco etapas:

| Etapa | Resultado esperado |
| --- | --- |
| Preproducción | GDD, alcance mínimo viable, prototipo y plan técnico. |
| Producción | Build jugable con sistemas, arte y contenido priorizados. |
| Pruebas | Corrección de defectos, playtests y validación de rendimiento. |
| Lanzamiento | Publicación en la plataforma elegida con ficha, clasificación y soporte activo. |
| Validación | Playtests, retroalimentación, análisis de resultados y decisión de continuidad. |

Quedan fuera de este primer ciclo: una oficina permanente, contratación de un equipo completo, publicidad masiva, desarrollo simultáneo para todas las consolas y contenido adicional que no esté aprobado en el alcance mínimo viable.

## 4. Prototipo mínimo viable

Antes de ampliar el alcance, el Prototipo debe cumplir como mínimo:

- Bucle principal de juego completo y comprensible.
- Tutorial o introducción que permita empezar sin asistencia.
- Sistemas principales documentados y probados.
- Arte y audio suficientes para comunicar la propuesta del juego.
- Guardado, configuración y salida funcionales.
- Rendimiento validado en los equipos objetivo.
- Sin defectos críticos abiertos.
- Licencias de código, audio, imágenes, fuentes y plugins verificadas.
- Revisión inicial de contenido y riesgos preparada para una futura distribución.

Las funcionalidades secundarias se incorporan únicamente si no ponen en riesgo el lanzamiento del núcleo jugable.

## 5. Uso sostenible de recursos

### Equipo humano

El primer producto opera con cuatro áreas esenciales:

| Área | Responsabilidad principal |
| --- | --- |
| Dirección General / CEO | Decisiones, contratos, presupuesto y aprobación de cambios. |
| Sistemas | Código, integración, builds, respaldos y seguridad. |
| Producción | Alcance, cronograma, riesgos, entregas y coordinación. |
| Diseño | GDD, niveles, mecánicas, experiencia y playtesting. |

Marketing y soporte se realizan inicialmente como responsabilidades distribuidas, sin crear una plaza adicional hasta que las ventas lo justifiquen.

### Equipo físico y servicios

- Cuatro laptops de desarrollo.
- Cuatro mouses económicos.
- Una tableta gráfica compartida.
- Un disco externo compartido para respaldos.
- Dos audífonos para pruebas de audio.
- Workspace limitado a cuatro horas mensuales a 80 Bs por hora.
- Herramientas gratuitas o de bajo costo mientras el producto no genere ingresos.

## 6. Plan de desarrollo por fases

| Fase | Actividades | Criterio para avanzar |
| --- | --- | --- |
| Preproducción | Definir visión, público, alcance, riesgos, arquitectura y prototipo. | El prototipo demuestra el núcleo jugable y el equipo aprueba el MVP. |
| Producción inicial | Construir sistemas principales y primera versión de contenido. | Existe una build jugable con el flujo principal completo. |
| Producción final | Integrar contenido, audio, UI, accesibilidad y optimización. | El alcance está congelado y no hay bloqueadores críticos. |
| QA y playtest | Pruebas funcionales, rendimiento, compatibilidad, usabilidad y contenido. | Los defectos críticos están en cero y los altos tienen decisión documentada. |
| Preparación de lanzamiento | Clasificación, ficha de tienda, precio, soporte, instalador y materiales. | La plataforma acepta la build y la documentación está completa. |
| Postlanzamiento | Soporte, parches, análisis de métricas y mejoras pequeñas. | Cada actualización tiene beneficio, costo y riesgo evaluados. |

## 7. Sustentabilidad técnica

- El repositorio tendrá ramas protegidas, revisión de cambios y etiquetas de versión.
- Se realizarán respaldos automáticos o manuales frecuentes del código y los assets.
- Cada build de prueba se asociará a un commit identificable.
- Las dependencias tendrán versión fijada y licencia registrada.
- La documentación mínima incluirá instalación, arquitectura, generación de build y recuperación ante pérdida de equipo.
- Se evitará depender de un único integrante para un sistema crítico.
- Las mejoras postlanzamiento priorizarán errores, rendimiento, seguridad y retención antes que nuevas funcionalidades grandes.

## 8. Sustentabilidad financiera

La empresa no asumirá costos permanentes hasta validar el producto. Antes de aprobar un gasto se revisará:

- Si es necesario para terminar o publicar el MVP.
- Si existe una alternativa gratuita, compartida o temporal.
- Si el gasto puede pagarse con la reserva sin comprometer el lanzamiento.
- Si produce una mejora medible en calidad, ventas, soporte o seguridad.
- Si requiere una obligación mensual posterior.

Los ingresos del primer producto se asignarán en este orden:

1. Comisiones, impuestos y obligaciones de venta.
2. Corrección de defectos, respaldos y continuidad del prototipo.
3. Recuperación de la reserva de 5.000 Bs si fue utilizada.
4. Honorarios y costos operativos pendientes.
5. Mejoras pequeñas del producto.
6. Reinversión en un segundo producto solo después de terminar y validar el Prototipo.

## 9. Validación comercial de bajo costo

Antes del lanzamiento se medirán señales de interés sin comprometer un presupuesto publicitario alto:

- Lista de deseados o registros de interés.
- Retención y duración de las sesiones de playtest.
- Conversión de la página de tienda.
- Comentarios repetidos sobre diversión, claridad y rendimiento.
- Costo real de producir una demo, tráiler o actualización.

La promoción inicial será orgánica: redes sociales, comunidades, eventos universitarios, creadores de contenido y demostraciones. La publicidad pagada solo se aprueba cuando exista una página de tienda validada, una audiencia identificada y una métrica de conversión que permita medir el retorno.

## 10. Mantenimiento y evolución del prototipo

Durante la validación del Prototipo se mantendrán:

- Canal oficial de soporte.
- Registro de errores y solicitudes.
- Priorización por severidad y cantidad de usuarios afectados.
- Parche para defectos críticos tan pronto como sea técnicamente posible.
- Comunicación clara de cambios y problemas conocidos.
- Revisión mensual de costos de plataforma, almacenamiento y herramientas.

No se prometerán actualizaciones, DLC, funciones online ni fechas de lanzamiento que el equipo no pueda mantener con sus recursos reales.

## 12. Riesgos y contingencias del primer producto

| Riesgo | Mitigación | Contingencia |
| --- | --- | --- |
| El alcance crece | Congelar el MVP y evaluar cada cambio por costo y plazo. | Eliminar funciones secundarias y proteger el núcleo jugable. |
| El presupuesto se agota | Mantener la reserva y evitar suscripciones no esenciales. | Pausar gastos, reducir alcance y solicitar aprobación extraordinaria. |
| Se pierde código o assets | Respaldos y repositorio protegido. | Restaurar desde el último respaldo y priorizar recuperación. |
| El juego no conecta con el público | Playtests tempranos y revisión de métricas. | Ajustar propuesta, demo, tutorial y comunicación antes de escalar marketing. |
| Una persona queda indisponible | Documentación, revisión cruzada y tareas compartidas. | Reasignar prioridades y contratar apoyo temporal si es imprescindible. |
| La plataforma rechaza la build | Checklist de requisitos desde producción. | Corregir bloqueadores y escalonar el lanzamiento por plataforma. |

## 13. Responsables

- **CEO:** aprueba gastos, contratos, cambios de alcance y decisiones de reinversión.
- **Producción:** mantiene el plan, el cronograma, los indicadores y la revisión mensual.
- **Sistemas:** conserva el repositorio, backups, builds, seguridad y documentación técnica.
- **Diseño:** protege la visión del juego, coordina playtests y prioriza mejoras de experiencia.
- **Equipo completo:** reporta riesgos, defectos, costos imprevistos y oportunidades de mejora.

## 14. Justificación de la proyección de ganancias

La gráfica financiera actualizada representa un **flujo acumulado** para el primer producto, después de cuatro meses de preparación. Se llegó a sus resultados aplicando dos cálculos separados:

```text
Ingreso neto por unidad = Precio de venta × (1 − comisión de plataforma)
Ingreso neto por unidad = 80 Bs × (1 − 0,30) = 56 Bs

Resultado mensual = (Unidades vendidas × 56 Bs) − costo fijo mensual
Flujo acumulado = saldo acumulado anterior + resultado mensual
```

Para los meses previos al lanzamiento, donde todavía no existen ventas, la fórmula es:

```text
P-4 = −21.790,60 Bs de arranque − 5.563,68 Bs de operación = −27.354,28 Bs
P-3, P-2 y P-1 = saldo anterior − 5.563,68 Bs
M1 en adelante = saldo anterior + resultado mensual
```

Por eso las ganancias de M1, M2 y M3 no se consideran utilidad libre: primero cubren el saldo negativo acumulado.

El costo fijo mensual utilizado en la proyección actualizada es de **5.563,68 Bs**: honorarios iniciales, workspace y depreciación referencial del equipo. Por lo tanto, el punto de equilibrio se obtiene así:

```text
Punto de equilibrio = 5.563,68 Bs / 56 Bs
Punto de equilibrio = 99,35 unidades
Punto de equilibrio redondeado = 100 unidades por mes
```

Los primeros cuatro meses se reservan para desarrollar el Prototipo y realizar el estudio de mercado. Durante ese período no se proyectan ventas y el saldo se vuelve negativo. Con la estructura austera, el primer mes posterior al lanzamiento alcanza 250 unidades y genera una ganancia operativa, pero esa ganancia no es todavía dinero disponible: primero reduce la deuda acumulada. El saldo total se recupera durante el mes 3 posterior al lanzamiento.

### Relación con el presupuesto del Prototipo

Esta proyección no reemplaza el presupuesto austero de **21.790,60 Bs** definido para desarrollar el Prototipo. Son dos escenarios diferentes:

| Elemento | Presupuesto del Prototipo | Proyección del PDF |
| --- | ---: | ---: |
| Propósito | Desarrollar, estudiar el mercado y validar el Prototipo | Estimar ventas después de la publicación |
| Base de costos | 21.790,60 Bs de arranque | 5.563,68 Bs de costo fijo mensual |
| Precio por unidad | Pendiente de validación | 80,00 Bs |
| Ingreso neto por unidad | Pendiente de validación | 56,00 Bs |
| Punto de equilibrio | 100 unidades/mes después del lanzamiento | 100 unidades/mes |

La decisión de avanzar se tomará con los datos reales del Prototipo: precio aprobado, comisión de la plataforma, unidades vendidas, devoluciones, impuestos y costos de soporte. No se utilizará la ganancia proyectada para justificar gastos antes de comprobar la demanda.

## 15. Revisión del plan

El plan se revisará al cierre de cada fase y mensualmente durante la validación. Se actualizará si cambia el alcance, el precio, la plataforma, el número de integrantes, el presupuesto, la clasificación de contenido o los resultados reales de ventas.

Ninguna decisión de iniciar un segundo producto debe comprometer la capacidad de terminar, validar y documentar el Prototipo.
