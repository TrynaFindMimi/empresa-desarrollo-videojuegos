# Sprints del Primer Prototipo

**Duración:** 4 meses antes del lanzamiento  
**Cadencia:** sprints de 2 semanas  
**Equipo:** CEO, Sistemas, Producción y Diseño  
**Objetivo:** obtener una versión jugable, validada y documentada para decidir si el producto continúa.

## Reglas de trabajo

- Cada sprint tiene un objetivo único y un entregable demostrable.
- El alcance se congela durante el sprint; los cambios pasan al backlog.
- La revisión se realiza el último día del sprint.
- Un sprint no se cierra si el entregable no tiene evidencia.
- Producción actualiza riesgos, cronograma y presupuesto en cada revisión.

## Sprint 0 · Preparación

| Elemento | Definición |
| --- | --- |
| Duración | 1 semana inicial |
| Objetivo | Organizar el equipo y preparar el estudio de mercado. |
| Actividades | Roles, repositorio, Trello, Notion, presupuesto, riesgos y calendario. |
| Entregables | Acta de inicio, tablero, registro inicial de riesgos y estructura del repositorio. |
| Criterio de salida | Todos conocen su responsabilidad y existe una fuente única de documentación. |

## Sprint 1 · Mercado y propuesta

| Elemento | Definición |
| --- | --- |
| Duración | 2 semanas |
| Objetivo | Comprobar para quién se desarrolla el Prototipo y qué problema de entretenimiento resuelve. |
| Actividades | Encuestas, análisis de competencia, definición del público y propuesta de valor. |
| Entregables | Informe de mercado, perfil de usuario y propuesta de valor. |
| Criterio de salida | El equipo puede explicar público, género, diferenciador y riesgo comercial principal. |

## Sprint 2 · GDD y alcance MVP

| Elemento | Definición |
| --- | --- |
| Duración | 2 semanas |
| Objetivo | Convertir la propuesta en un alcance pequeño y realizable. |
| Actividades | Mecánicas, reglas, flujo de juego, niveles, referencias visuales y criterios de aceptación. |
| Entregables | GDD inicial, backlog priorizado y definición del MVP. |
| Criterio de salida | Cada función del MVP tiene responsable, esfuerzo estimado y condición de terminado. |

## Sprint 3 · Base técnica

| Elemento | Definición |
| --- | --- |
| Duración | 2 semanas |
| Objetivo | Preparar la arquitectura y probar las decisiones técnicas críticas. |
| Actividades | Proyecto base, control de versiones, escenas, input, guardado y pipeline de build. |
| Entregables | Build técnica, arquitectura documentada y primera prueba de instalación. |
| Criterio de salida | La build se genera desde un commit identificado y puede ser recuperada por otro integrante. |

## Sprint 4 · Bucle principal

| Elemento | Definición |
| --- | --- |
| Duración | 2 semanas |
| Objetivo | Hacer jugable la acción principal del Prototipo. |
| Actividades | Mecánica central, controles, feedback, condición de éxito y condición de fallo. |
| Entregables | Primera build jugable de principio a fin. |
| Criterio de salida | Una persona externa puede jugar sin explicación extensa y entender el objetivo. |

## Sprint 5 · Vertical slice

| Elemento | Definición |
| --- | --- |
| Duración | 2 semanas |
| Objetivo | Integrar una pequeña sección con calidad representativa del resultado esperado. |
| Actividades | Arte provisional consistente, audio, UI, iluminación y flujo completo. |
| Entregables | Vertical slice y checklist de calidad. |
| Criterio de salida | La sección demuestra dirección visual, experiencia y viabilidad técnica. |

## Sprint 6 · Playtest y aprendizaje

| Elemento | Definición |
| --- | --- |
| Objetivo | Validar si el Prototipo se entiende y resulta atractivo. |
| Actividades | Sesiones de prueba, encuestas, observación, medición de abandono y registro de defectos. |
| Entregables | Informe de playtest, backlog de ajustes y decisión de continuar, cambiar o reducir alcance. |
| Criterio de salida | Las decisiones se basan en evidencias y no solo en opiniones del equipo. |

## Sprint 7 · Corrección y rendimiento

| Elemento | Definición |
| --- | --- |
| Duración | 2 semanas |
| Objetivo | Corregir problemas prioritarios y asegurar que el Prototipo sea estable. |
| Actividades | Bugs, rendimiento, compatibilidad, accesibilidad básica y revisión de licencias. |
| Entregables | Release candidate, reporte de pruebas y matriz de riesgos actualizada. |
| Criterio de salida | No existen defectos críticos y los riesgos altos tienen mitigación y contingencia. |

## Sprint 8 · Presentación y decisión

| Elemento | Definición |
| --- | --- |
| Duración | 2 semanas |
| Objetivo | Preparar una presentación sólida y decidir el siguiente paso. |
| Actividades | Trailer o demo, ficha de producto, clasificación preliminar, presupuesto y revisión ejecutiva. |
| Entregables | Build presentable, documentación final y decisión de continuidad. |
| Criterio de salida | El CEO y Producción deciden continuar, ajustar el alcance o cerrar el Prototipo con sus aprendizajes. |

## Revisión de sprint

| Momento | Pregunta | Evidencia |
| --- | --- | --- |
| Inicio | ¿Qué objetivo es prioritario y qué riesgo puede bloquearlo? | Sprint planning y tarjeta de riesgo. |
| Durante | ¿La tarea avanza o necesita ayuda? | Tablero actualizado y daily. |
| Cierre | ¿Qué se terminó realmente? | Build, documento, prueba o informe. |
| Retrospectiva | ¿Qué cambiaremos en el siguiente sprint? | Acta y acción con responsable. |

## Regla de decisión

Si dos sprints consecutivos entregan menos del 70 % de lo comprometido, Producción debe activar la revisión de R01, reducir el alcance secundario y reprogramar el Gantt antes de añadir trabajo nuevo.
